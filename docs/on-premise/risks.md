# Atmos On-Premise — Risks

Application risks (OpenWeather, MongoDB, Redis unavailable) are the same as in the cloud version: see [cloud risks](../cloud/risks.md). This file lists the risks of the on-premise platform. The risks are reviewed again after the implementation.

| Risk | Impact | Mitigation |
|---|---|---|
| Host PC failure or reinstall | The whole platform is unavailable | All configuration is in Git; the servers are recreated with `vagrant up` and `site.yml` |
| Host restarts without warning (Windows update, power loss) | Servers stop unsafely; the cluster or data can break | Windows active hours and update pause; stop the servers with `vagrant halt` before updates; `clean` snapshots for a rebuild |
| Not enough RAM on the host | Servers swap, pods are killed (OOM), Windows becomes slow | About 10.6 GB available: the application servers use 9 GB and `jenkins` runs only for CI; memory limits on every pod and container; 1 GB swap file on `nexus-traefik` and `jenkins`; no log storage; Prometheus retention 3 days |
| `nexus-traefik` down | No registry and no HTTPS access to Jenkins and Nexus; running pods continue, but no pod can start with a new image | Starts first; memory limits on Nexus and Traefik; server health visible in Grafana; rebuild from the `clean` snapshot and Ansible |
| `k8s-cp` down (single control plane) | Running pods continue, but deploys and rescheduling stop | Start order `nexus-traefik`, `jenkins`, `k8s-cp`, `k8s-w1`; rebuild from the `clean` snapshot and Ansible |
| Drive D: of the host PC full (VM disks are dynamic, about 110 GB free) | Servers stop writing; data can be damaged | Nexus cleanup policy; Jenkins removes images after a build; free disk of each server in Grafana; free space on D: checked with `fsutil volume diskfree D:` |
| Disk with MongoDB data lost (local-path) | Weather history is lost | Manual `mongodump` before risky changes; data is not critical |
| VM creation fails (Vagrant on Windows, box download fails) | Servers cannot be created or rebuilt | Pinned VirtualBox, Vagrant and box versions; `vagrant up` skips existing servers and can be run again; `clean` snapshots |
| The Mac cannot reach the host PC over SSH | Servers keep running, but cannot be started, stopped or rebuilt from the Mac | DHCP reservation for the host PC; the OpenSSH server starts with Windows; fallback: run the `vagrant` commands on the PC itself |
| IP conflict or a new address of the Mac or the host PC | Servers are unreachable, `*.atmos.lan` names stop working; SSH and `kubectl` are blocked by `ufw` | Fixed server addresses outside the router DHCP range; DHCP reservations for the Mac and the host PC |
| Build on `jenkins` uses more RAM than planned (0.1 GB free) | The kernel stops Jenkins (OOM); Nexus and the application are not affected | One Jenkins executor; memory limit on Jenkins; build peak checked in Grafana; if needed, move 0.5 GB from `k8s-w1` to `jenkins` |
| Docker bypasses `ufw` | Ports published by Docker are open to the whole home network | Traefik and Jenkins in the host network; Nexus published only on `127.0.0.1`; ports checked from another device in the home network |
| Disk full: Nexus blob store on `nexus-traefik`, images and build cache on `jenkins` | Images cannot be pushed, builds fail | Nexus cleanup policy (keep the last N tags) and compact blob store task; Jenkins removes local images and the build cache after a build; free disk visible in Grafana |
| Self-signed CA not trusted somewhere | Docker push, image pull or Flux scan fails; browser warnings | Ansible distributes the CA to Docker on `jenkins`, the cluster nodes and the Mac; Flux gets it as a Secret; name in the SAN field |
| Certificate expires | Registry and tools stop working over HTTPS | CA valid for 10 years; server certificate valid for at most 825 days (browser limit); expiry date written in `README.md` of `atmos-ansible`; certificate recreated by Ansible |
| Jenkins compromised or its credentials leaked | Jenkins has the Docker socket, so it controls the `jenkins` VM (not Nexus or Traefik); it can push an image that Flux deploys automatically | Jenkins reachable only through Traefik (`ufw`: port 8080 only from `nexus-traefik`); Nexus push user and read-only deploy key only; no kubeconfig and no access to `atmos-k8s`; a bad image is rolled back with Git |
| Jenkins build numbers start again at 1 after a rebuild of `jenkins`, while Nexus keeps higher tags | The numerical image policy keeps the old image, new builds are not deployed | After a rebuild of `jenkins`, set Next Build Number of the job above the highest tag in Nexus (rebuild steps in `architecture.md`) |
| A rebuilt `k8s-w1` cannot join the cluster | The node is rejected (old node password in the cluster) | `kubectl delete node k8s-w1` before the join; the rebuild steps are in `architecture.md` |
| Flux deploy key or bootstrap token leaked | Attacker can change `atmos-k8s` or other repositories | Deploy key with write access to `atmos-k8s` only, revoked and rotated in GitHub if leaked; bootstrap token short-lived and revoked after use |
| Vault password or secrets committed by mistake | Platform credentials leak | `.gitignore` in every platform repository; vault password stays on the Mac, outside the repository; app secrets are created by hand |
| Rollback undone by image automation | Flux deploys the broken image again after `git revert` | Suspend the image update automation before the revert |
| No central log storage | Logs of restarted or deleted pods are lost | `kubectl logs --previous` for the last restart; metrics in Grafana |
| Version drift after a rebuild | Platform behaves differently after a rebuild | Versions pinned in Ansible `group_vars/`; Helm chart versions pinned in `atmos-k8s` |
| Repository `atmos-k8s` confused with the k3s installation | k3s settings are added to the wrong repository and are not applied | The rule is documented in `architecture.md` (section 7): k3s install and node settings in `roles/k3s/` of `atmos-ansible`; cluster workloads in `atmos-k8s` |
