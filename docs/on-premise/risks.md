# Project Atmos On-Premise — Risks

Application risks (OpenWeather, MongoDB, Redis unavailable) are the same as in the cloud version: see [cloud risks](../cloud/risks.md). This file lists the risks of the on-premise platform. The risks are reviewed again after the implementation (US-07).

| Risk | Impact | Mitigation |
|---|---|---|
| Host PC failure or reinstall | The whole platform is unavailable | All configuration is in Git; the servers are recreated with `vagrant up` and `site.yml` |
| Host restarts without warning (Windows update, power loss) | Servers stop unsafely; the cluster or data can break | Windows active hours and update pause; stop the servers with `vagrant halt` before updates; `clean` snapshots for a rebuild |
| VirtualBox runs on top of Hyper-V, because WSL2 needs it | Servers are slower; some VirtualBox features can be unstable | Pinned VirtualBox version that supports Hyper-V; create and test one server first in US-02; if the servers are too slow, the fallback is to turn off WSL2 and Hyper-V, run Vagrant in Windows and Ansible in a small Linux admin VM (a change of the architecture, decided with a new ADR) |
| Not enough RAM on the host | Servers swap, pods are killed (OOM), Windows becomes slow | Planned resource budget; memory limits on every pod and container; WSL2 limited in `.wslconfig`; no log storage; Prometheus retention 3 days; stop the servers when the PC is used for other things |
| `k8s-cp` down (single control plane) | Running pods continue, but deploys and rescheduling stop | Start order `tools`, `k8s-cp`, `k8s-w1`; rebuild from the `clean` snapshot and Ansible |
| Disk with MongoDB data lost (local-path) | Weather history is lost | Manual `mongodump` before risky changes; data is not critical |
| VM creation fails (Vagrant from WSL2 cannot control VirtualBox on Windows, box download fails) | Servers cannot be created or rebuilt | Pinned Vagrant and box versions; WSL2 settings documented in `README.md` of `project-atmos-onprem-ansible` (`VAGRANT_WSL_ENABLE_WINDOWS_ACCESS`, project on `/mnt/c`, synced folder off, SSH key in the WSL2 home folder); `vagrant up` skips existing servers and can be run again; `clean` snapshots |
| IP conflict or a new address of the host PC | Servers are unreachable, `*.atmos.lan` names stop working; SSH and `kubectl` are blocked by `ufw` | Fixed addresses outside the router DHCP range; DHCP reservation for the host PC |
| Build on `tools` uses more RAM than planned (0.1 GB free) | The kernel stops Nexus or Jenkins (OOM) | One Jenkins executor; memory limits on Jenkins and Nexus; build peak checked in Grafana; if needed, move RAM from the free pod budget of `k8s-w1` to `tools` |
| Docker bypasses `ufw` | Ports published by Docker are open to the whole home network | Traefik in the host network; Jenkins and Nexus published only on `127.0.0.1`; port check from another device in US-03 |
| Disk on `tools` full (Nexus images, Docker build cache) | New images cannot be pushed, builds fail | Nexus cleanup policy and compact blob store task; Jenkins removes local images and the build cache after a build; free disk visible in Grafana |
| Self-signed CA not trusted somewhere | Docker push, image pull or Flux scan fails; browser warnings | Ansible distributes the CA to Docker, the cluster nodes and the admin machine; Flux gets it as a Secret; name in the SAN field; the check is part of US-03 to US-05 |
| Certificate expires | Registry and tools stop working over HTTPS | CA valid for 10 years; server certificate valid for at most 825 days (browser limit); expiry date written in `README.md` of `project-atmos-onprem-ansible`; certificate recreated by Ansible |
| Jenkins compromised or its credentials leaked | Jenkins has the Docker socket, so it controls `tools`; it can push an image that Flux deploys automatically | Jenkins reachable only through Traefik from the home network; Nexus push user and read-only deploy key only; no kubeconfig and no access to `project-atmos-onprem-k3s`; a bad image is rolled back with Git |
| Jenkins build numbers start again at 1 while Nexus keeps higher tags | The numerical image policy keeps the old image, new builds are not deployed | Rebuild `tools` as a whole (Jenkins and Nexus together); if only Jenkins is rebuilt, set the next build number above the newest tag in Nexus |
| A rebuilt `k8s-w1` cannot join the cluster | The node is rejected (old node password in the cluster) | `kubectl delete node k8s-w1` before the join; the rebuild steps are in `architecture.md` |
| Flux deploy key leaked | Attacker can change `project-atmos-onprem-k3s` | Key has write access to that one repository only; revoke and rotate in GitHub |
| GitHub token for the Flux bootstrap leaked | Access to GitHub repositories | Short-lived token, revoked after the bootstrap |
| Vault password or secrets committed by mistake | Platform credentials leak | `.gitignore` in every platform repository; vault password stays outside the repository; app secrets are created by hand |
| Rollback undone by image automation | Flux deploys the broken image again after `git revert` | Suspend the image update automation before the revert |
| No central log storage | Logs of restarted or deleted pods are lost | `kubectl logs --previous` for the last restart; metrics in Grafana |
| Version drift after a rebuild | Platform behaves differently after a rebuild | Versions pinned in Ansible `group_vars/`; Helm chart versions pinned in `project-atmos-onprem-k3s` |
| One user story changes two repositories (US-03, US-04, US-06 also change `project-atmos-onprem-ansible`) | A story is closed while its Ansible part is missing; a rebuild does not give the tested result | The issue lists the work per repository in **Details**; Pull Requests in both repositories link the issue; the story is checked after a fresh `site.yml` run |
| Repository `project-atmos-onprem-k3s` confused with the k3s installation | k3s settings are added to the wrong repository and are not applied | The rule is documented in `architecture.md` (section 7): k3s install and node settings in `roles/k3s/` of `project-atmos-onprem-ansible`; cluster workloads in `project-atmos-onprem-k3s` |
